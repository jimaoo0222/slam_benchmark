# 外参修正后全量重跑（2026-11-05）

## 0. 为什么重跑

之前 32 次运行的 IMU↔LiDAR 外参是错的，四份配置各错各的：

| 算法 | 之前填的 | 问题 |
|---|---|---|
| GLIM | MID-360s 的 `T_lidar_imu` | C01 的 4 个包也在用它 |
| FAST-LIO2 | MID-360s 的 `extrinsic_T` | 同上（但有在线估计兜着） |
| Point-LIO | `[+0.011, +0.02329, −0.04412]` | C01 用了 MID-360 的值，**而且符号是反的** |
| LIO-SAM | `[0, 0, 0]` | 假设 IMU 与雷达同点，丢掉 4.4 cm 的 Z 向杠杆臂 |

2026-11-05 拿到 C01 官方驱动（`driver/Skylandx_ros_driver`），其中给出了
C01 的标定值 `(18.90, 24.64, −53.5) mm`。四份配置现已按官方值改正，
见 [docs/01 第 5 节](../../docs/01_MID360_vs_C01_雷达对比.md)。

## 1. 怎么跑的

一条命令：

```bash
bash scripts/29_rerun_all.sh              # 8 包 × 4 算法 = 32 次，断点续跑
python3 scripts/30_eval_all.py            # 统一评测，自动挑停车窗口
```

每个组合的配置由 `scripts/lib_radar.sh` 按包名前两位自动选
（`01_`/`02_` → MID-360s，`03_`/`04_` → C01），不会拿错外参。

### 回放倍率

| 算法 | MID-360s | C01 | 原因 |
|---|---|---|---|
| GLIM | 离线 | 离线 | 直接读 bag，比实时快 |
| FAST-LIO2 | 1.0 | 1.0（03_02 用 0.7）| 帧式，一帧一次 IEKF 更新，跟得上 |
| LIO-SAM | 1.0 | **0.7** | 帧式，但特征提取 + 因子图较重，1.0 时丢约 16% 帧 |
| Point-LIO | 1.0 | **0.35** | **逐点** IEKF，21.7 万点/秒，这颗 CPU 只能跑到 0.35 倍 |

> 降速只影响「给 CPU 留多少时间」，**输入一个点都没少**，不影响精度结果。
> 这是 Point-LIO 在 C01 数据量下的固有代价。

### 并行跑要注意

16 核机器上可以把不同组合并行，但**必须给每一路不同的 `ROS_DOMAIN_ID`**
（`--domain 11` / `--domain 12` …），否则四个算法共用的 `/livox/lidar`
会导致 `16_pc2_to_custom.py` 把别人的数据一起收进去。

> 本轮踩过一次：04_01 的 Point-LIO / LIO-SAM 在三路并行时被算力挤掉，
> 轨迹分别只覆盖 132/159 s 和 83/159 s，**误差虚高到 61 cm 和 240 cm**。
> 隔离重跑后恢复 0.6 cm 和 1.1 cm。教训是并行度不要超过 3，且要看覆盖率。

## 3. 和旧结果的差别

C01 的四个包（这是修正外参直接影响的部分）：

|---|---|---|---|---|

| 03_01 | LIO-SAM | 4.7 | 4.9 | +0.2 |
| 03_01 | Point-LIO | 3.2 | 7.2 | +4.0 |
| 03_01 | FAST-LIO2 | 7.8 | 8.1 | +0.3 |
| 03_02 | GLIM | 4.8 | **1.8** | **−3.0** |
| 03_02 | LIO-SAM | 1.9 | **1.4** | −0.5 |
| 03_02 | FAST-LIO2 | 2.0 | **1.6** | −0.4 |
| 03_02 | Point-LIO | 4.9 | **4.0** | −0.9 |
| 04_01 | GLIM | 0.5 | 0.5 | 0 |
| 04_01 | Point-LIO | 0.6 | 0.6 | 0 |

| 04_02 | Point-LIO | 0.5 | **0.4** | −0.1 |
| 04_02 | FAST-LIO2 | 0.5 | **0.4** | −0.1 |

C01 四包平均：GLIM 2.85 → **1.92 cm**（−33%）；LIO-SAM 2.10 → **2.00**；
FAST-LIO2 3.00 → 2.96；Point-LIO 2.30 → 3.05。

**03_01 的数字变动最大，原因有两个，都修掉了：**

1. 外参错（C01 借用了 MID-360 的值）。
2. **评测脚本的 bug**：`--stop-from` 在参考轨迹上找停车点时**没有重试机制**，
   而各算法自己检测时有。03_01 的 FAST-LIO2 需要把 `min_dur` 放宽到 0.6 s
   才能检出全部 7 个停车点，参考轨迹这步却只检出 6 个就放弃，于是四条轨迹
   全部退回各自检测 —— 噪声大的轨迹会把同一次停顿拆成几段，导致**停车点和
   真值错位配对**，误差虚高到 400 cm 以上。

   现在 `--stop-from` 也做了同样的重试，并且**用对齐尺度自校验**
   （尺度偏离 1 超过 3% 就认为窗口配错，继续换参数），不会再静默产出垃圾数字。
